# Story 1.3: Notificações ao funcionário em aprovação/rejeição

## Status: Approved

## Description

Como **funcionário**, quero receber notificação (in-app + email) quando meu relatório for aprovado ou rejeitado, **para** não precisar abrir o app o tempo todo verificando status.

> **Contexto:** hoje, após o gestor decidir, o funcionário só descobre se navegar manualmente em "Relatórios". Provedor de email confirmado pelo usuário: **Resend** (default).

## Acceptance Criteria

- [ ] **Given** sou funcionário e meu relatório foi decidido (approved ou rejected), **when** acesso o app, **then** vejo um badge numérico vermelho ao lado do item "Relatórios" no menu lateral/bottom nav indicando quantas decisões eu ainda não vi.
- [ ] **Given** o badge mostra `2`, **when** clico em "Relatórios" e abro um relatório com decisão pendente de visualização, **then** essa decisão é marcada como vista (`notification_read_at = now()`) e o badge atualiza para `1` na próxima visita ao menu.
- [ ] **Given** sou funcionário, **when** meu relatório é aprovado, **then** recebo um email com:
  - Assunto: `Seu relatório "[título]" foi aprovado`
  - Corpo: nome do aprovador, comentário (se houver), valor total, link `https://<dominio>/app/reports/[id]`
  - Idioma: pt-BR
- [ ] **Given** meu relatório é rejeitado, **when** o email é enviado, **then** o assunto é `Seu relatório "[título]" foi rejeitado` e o corpo destaca o comentário (motivo) com formatação de alerta.
- [ ] **Given** o admin auto-aprova o próprio relatório (já permitido), **when** a decisão é gravada, **then** **nenhum email é enviado** ao admin para si mesmo.
- [ ] **Given** estou em mobile (390x844), **when** abro o email, **then** o layout é responsivo, o link/botão tem altura ≥44px e leva direto à rota correta.
- [ ] **Given** o envio do email falha (Resend down ou indisponível), **when** o RPC `admin_decide_report` é chamado, **then** a decisão é gravada normalmente (transação não bloqueia) e a falha é logada — não impedir o fluxo de aprovação por falha de email.

## Technical Notes

### Migration aditiva
- **Arquivo:** `supabase/migrations/<timestamp>_notifications.sql` (novo)
- Adicionar coluna em `report_approvals`:
  ```sql
  ALTER TABLE public.report_approvals
    ADD COLUMN notification_read_at TIMESTAMP WITH TIME ZONE NULL;
  CREATE INDEX idx_report_approvals_unread
    ON public.report_approvals (report_id)
    WHERE notification_read_at IS NULL;
  ```
- **Reforçar:** **migration apenas aditiva** (regra global). Não alterar dados existentes.

### Edge function nova
- **Arquivo:** `supabase/functions/send-report-decision-email/index.ts` (novo)
- **Provedor:** Resend (https://resend.com/)
- **Secrets necessários:** `RESEND_API_KEY` (DevOps adiciona junto da OPENAI no Story 1.1)
- **Payload de entrada:**
  ```json
  {
    "report_id": "uuid",
    "decision": "approved" | "rejected",
    "comment": "string|null",
    "approver_name": "string"
  }
  ```
- **Lógica:**
  1. Validar `RESEND_API_KEY` presente; se não, retornar 503 com `{ code: "EMAIL_UNAVAILABLE" }` (mesmo padrão da Story 1.1).
  2. Carregar `report` + `profile` do owner via service role (a função roda com privilégios elevados).
  3. Se `report.user_id === approver_id`: retornar 200 `{ skipped: true, reason: "self_approval" }`. **Não enviar email.**
  4. Montar HTML mínimo (template inline) em pt-BR, mobile-friendly (table layout 600px max).
  5. Chamar `https://api.resend.com/emails` com `from: "oxyve <noreply@<dominio-confirmado>>"`, `to: profile.email`, subject e html.
  6. Em qualquer erro do Resend, retornar 500 com payload de erro mas **não rethrow** (caller já não bloqueia em falha).

### Trigger / chamada
**Decisão de arquitetura:** chamar a edge function **a partir do RPC `admin_decide_report`** via `pg_net.http_post` (mais simples que webhook trigger, transação local controlada).

- **Arquivo:** nova migration `supabase/migrations/<timestamp>_admin_decide_report_v2.sql`
- Recriar `admin_decide_report` com `CREATE OR REPLACE FUNCTION` (já existe na migration de 2026-02-08).
- **Após o INSERT em `report_approvals`** (linha 110-111 da migration original), adicionar bloco PERFORM `net.http_post(...)` chamando a edge function. Falhas são logadas mas não fazem `RAISE`.
- Garantir que `net` extension está habilitada: `CREATE EXTENSION IF NOT EXISTS pg_net;`. Se não estiver disponível no plano Supabase, fallback: chamar a edge function direto do frontend após sucesso do `useApproveReportRpc.mutateAsync` (mais simples mas menos resiliente). **Decidir junto com DevOps no início da story.**

### Frontend in-app badge
- **Hook novo:** `src/hooks/useUnreadDecisions.ts`
  - Query `report_approvals` filtrando: `report.user_id = current_user_id` e `notification_read_at IS NULL`.
  - Retorna `count: number` e tipos `UnreadDecision[]`.
  - Polling: usar `refetchInterval: 60_000` (1min) — não justifica realtime ainda.
- **UI no menu:**
  - **Arquivo:** `src/components/layout/SidebarNav.tsx` — onde renderiza item "Relatórios", adicionar `<Badge>` se `count > 0`.
  - **Arquivo:** `src/components/layout/BottomNav.tsx` — **será criado na Story 3.5**, então este story só endereça o menu lateral atual. Adicionar TODO no código apontando que BottomNav herdará o mesmo padrão.
- **Marcação como lida:**
  - **Arquivo:** `src/pages/app/ReportDetail.tsx`
  - No `useEffect` quando o relatório carrega: se `report.user_id === current_user`, executar `supabase.from('report_approvals').update({ notification_read_at: new Date().toISOString() }).eq('report_id', id).is('notification_read_at', null)`.
  - Após sucesso, invalidar `['unread-decisions']` no React Query.

### Template de email (resumo do conteúdo)
```
Assunto: Seu relatório "{report.title}" foi {aprovado|rejeitado}

Olá, {profile.full_name}!

Seu relatório de despesas foi {aprovado|rejeitado} por {approver_name}.
{Se rejected: bloco destacado com comment}

Total: {formatCurrency(report.total_cents)}
{N} despesa(s)

[Ver relatório completo]   ← botão azul, h≥44px

— oxyve
```
HTML: tabela centralizada 600px max-width, fontes web-safe, sem CSS externo. Pode usar template builder simples (sem libs pesadas).

## Testing Requirements

### Manual (E2E)
1. Como funcionário (`user A`), criar relatório com 2 despesas e submeter.
2. Como gestor (`user B`), abrir fila e **aprovar** com comentário.
3. Como `user A`, recarregar app: badge "1" deve aparecer no menu Relatórios.
4. Caixa de entrada de `user A` deve receber email com assunto "Seu relatório ... foi aprovado".
5. Clicar no link do email: abrir direto a rota `/app/reports/:id`. Após carregar, badge desaparece.
6. Repetir cenário 2 com **rejeitar** e validar email + visual.
7. Como admin (`user C` que é também owner), **auto-aprovar** próprio relatório: NÃO deve receber email.

### Smoke mobile (390x844)
- Email aberto no Gmail mobile do iPhone Safari → layout responsivo, botão clicável.
- Badge no menu visível e legível.

### Edge cases
- Resend down → decisão é gravada, badge ainda aparece (in-app não depende do email).
- Funcionário sem `email` em `profiles` → função pula envio + loga warning.
- Múltiplas aprovações no mesmo relatório (não deveria acontecer hoje, mas se acontecer): badge conta cada uma; ao abrir relatório, todas marcadas como lidas.
- RLS: validar que `user A` não consegue ver `notification_read_at` de relatórios de `user B`.
